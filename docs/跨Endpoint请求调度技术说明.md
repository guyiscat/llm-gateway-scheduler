# 基于请求优先级与负载状态的跨 Endpoint 请求调度

本文依据项目当前的核心调度与本地模拟实现修订，描述已实现的请求接入、候选过滤、繁忙判断、窗口排序、端点选择及执行反馈。SLO 参数接口和历史性能缓存已经保留；成本–性能 Pareto 优化、SLO 约束筛选及执行失败后的自动重试属于后续扩展方向。

由于供应商、部署环境、计算硬件和资源分配策略等因素的差异，即使多个 Endpoint 支持相同模型，其容量限制、接口能力、服务时延和价格也可能不同。请求负载与资源占用又会随时间变化，因此端点选择需要结合请求特征及当前状态进行判断。

本项目在请求目标模型已经确定的前提下，围绕 Endpoint 选择建立模块化调度流程。当前机制包括五个主要阶段：请求规范化与分层过滤、优先级及模型候选池繁忙判断、繁忙窗口聚合与排序、统一端点选择，以及资源预留与执行反馈。默认路由策略为最小 RPM 利用率策略 `min_rpm`，排序与路由均可以独立替换。

## 1. 请求描述、数据处理与候选 Endpoint 过滤

### 1.1 标准请求及 SLO 接口

调度器接收完整的 `SchedulerRequest`，而不是单独的 Prompt 文本。每条请求自带目标模型 `target_model`，并包含请求标识、输入 Token 数、预计输出 Token 数、优先级、到达时间、消息内容、调用模式、接口类型、可选输出上限、SLO 和附加参数。

其中，`predicted_output_tokens` 表示调度时可使用的输出长度估计，用于分类、排序和 TPM 预留；`max_tokens` 表示可选的生成上限，两者含义不同。设置输出长度估计并不会自动截断生成结果。

当前 `SLO` 支持 `e2e_ms`、`ttft_ms` 和 `tpot_ms` 三个可选字段，分别表示端到端时延、首 Token 时延和平均输出 Token 间隔约束。框架会校验和保留这些参数，并将完整请求传给路由策略；默认策略尚未使用它们进行可行性筛选、评分或超时淘汰。请求结构目前没有专用的成本预算字段，也没有剩余预算的扣减机制。

### 1.2 本地数据集与请求生成

本地模拟从原始 Prompt/Response 数据集读取记录，使用固定的 Qwen tokenizer 计算输入和记录响应的 Token 长度。输入计数包含对话模板及相关工具参数的影响。该长度是统一实验口径下的 tokenizer 代理量，不应直接当作所有 Endpoint 的实际计费 Token 数。

数据处理层生成标准请求，流量模拟层按照固定间隔、随机间隔或突发到达模式提交请求。目标模型优先使用记录自身的字段，缺失时使用模拟配置的默认值；当前默认值为 `deepseek-flash`。该默认值仅补全缺失模型，不覆盖请求已明确指定的模型。

当前模拟配置采用 `prediction_mode=oracle`：记录没有显式输出估计时，使用历史 Response 的实际长度作为估计。这是一种实验基线，并非在线输出长度预测器。项目也支持固定估计模式，以及直接使用数据记录提供的 `predicted_output_tokens`。核心调度模块只读取标准请求中的估计值；历史实际长度由模拟执行器单独使用。

### 1.3 分层过滤

过滤模块产生三个集合，分别承担不同职责：

| 集合 | 条件 | 用途 |
| --- | --- | --- |
| `compatible` | 支持目标模型、所需接口及已知上下文长度要求 | 判断是否存在能够处理该请求的端点 |
| `eligible` | 在 compatible 基础上，要求健康且不处于 Cooldown | 作为模型候选池繁忙判断及路由范围的基础 |
| `feasible` | 在 eligible 基础上，满足当前已知 RPM、TPM 和并发硬容量 | 判断是否能够立即预留资源并派发 |

上下文长度检查使用输入长度加输出需求：请求提供 `max_tokens` 时使用该上限，否则使用预计输出长度。已知上下文上限不足的端点进入排除集合。

容量已满的端点仍保留在 eligible 中，参与繁忙判断，避免先把繁忙端点全部过滤掉，再将空集合误判为空闲。所有请求在实际派发前重新检查兼容性、健康、Cooldown 和硬容量，高优先级也不绕过这些条件。

没有兼容端点时，调度器明确拒绝请求。兼容端点暂时不健康、处于冷却或容量不足时，请求可以保留在等待队列中。若请求所需的预留 Token 数超过所有兼容端点的已知 TPM 上限，也会明确拒绝。当前核心没有基于剩余 SLO 决定等待期限的机制，也没有将请求交回上层重新选择模型的接口。

RPM、TPM 或并发上限为 `None` 时表示容量未知。未知项不参与该项硬容量和软繁忙阈值判断，使用量仍被统计，利用率保持未知；这不代表端点的实际容量无限。

## 2. Endpoint 运行状态与历史性能维护

每个 Endpoint 的静态配置包含唯一标识、支持模型、接口类型、可选上下文上限、输入和输出单价，以及 RPM、TPM 和并发上限。价格字段已可由路由上下文读取，但默认 `min_rpm` 不使用价格进行选择，当前离线端点配置的输入和输出价格均为零。

运行状态由统一的 `EndpointStateManager` 管理，包括滚动窗口内的请求数、预留及已修正 Token 数、在途并发、健康标记、冷却截止时间、失败统计和累计用量。候选检查、繁忙判断和资源预留复用该状态来源。

RPM 与 TPM 使用固定的 60 秒滚动窗口。时刻 t 的额度统计对应区间 `(t−60000, t]`，每次预留从其派发时刻起满 60 秒后过期。到达、时钟推进、反馈和快照读取都会清理过期项；没有每分钟整点统一清零的过程。

并发量与滚动额度分别维护。即使一个长请求的 RPM 记录已经过期，只要执行反馈尚未完成，它仍占用并发槽。因此，RPM 为零不能单独证明没有请求正在执行。

历史缓存按 Endpoint 标识组织，默认保留最近 60 秒的完成样本，每个端点最多保留 10000 条。缓存增量维护样本数、成功数、失败数及成功样本的平均 E2E、TTFT、TPOT；未观测到的指标保持未知。路由策略读取缓存统计，不必扫描完整请求日志。

当前历史缓存没有按模型、流式模式或 Token 长度建立细分索引，也没有实现长度相似性加权、时间衰减加权或置信度估计。核心默认补充的 E2E 为“请求到达到执行完成”的时长，包含调度等待；模拟结果另外区分窗口等待、容量等待和服务时间，但这些分项尚未形成端点条件化性能预测器。

## 3. 请求优先级与模型候选池繁忙判断

### 3.1 高、低两级优先级

模拟层与核心都只使用两级优先级：`priority=1` 表示高优先级，`priority=0` 表示低优先级。数据中明确提供的二分类值予以保留。

缺少显式值时，默认 binary 模式依据 request_id 和 priority_seed 生成可复现的二分类值，high_priority_ratio 默认 0.1；这是生成概率，不保证每个有限批次恰好 10% 为高优先级。uniform 模式将缺少值的请求全部设为低优先级。

四档字段、生成方式、核心映射和专用排序适配已移除。请求等级与轻/重分类互相独立：高优先级也可能是重请求，低优先级也可能是轻请求。

### 3.2 单端点与候选池繁忙条件

对于请求对应的非空 eligible 集合，任一端点满足以下任一条件，即判定该端点繁忙：

\[
R_e/R_e^{max} \geq \alpha_R
\quad\lor\quad
T_e/T_e^{max} \geq \alpha_T
\quad\lor\quad
N_e \geq C_e-r
\]

其中，R_e 和 T_e 是滚动窗口请求数与 Token 用量，N_e 是在途并发，C_e 是并发上限；默认 `α_R=α_T=0.95`，并发保留量 `r=3`。这些参数由配置控制。还可设置并发利用率阈值，此时并发繁忙门槛改为 `ceil(C_e×阈值)`，替代“上限减保留量”的方式。

只有该请求目标模型的 eligible 集合中所有端点均繁忙，才判定该模型候选池繁忙。判断范围由当前请求决定，不要求整个项目中所有其他模型的端点同时繁忙。空 eligible 集合不会被认定为“全部繁忙”。

请求到达强度不直接参与这个判定。分类模块使用的并发与待执行请求压力是另一套计算，用于调整重请求分类阈值，不决定请求是否进入调度窗口。

### 3.3 三条调度路径

| 请求与负载情况 | 调度路径 | 实际派发时的候选范围 |
| --- | --- | --- |
| 高优先级请求 | 跳过窗口，进入高优先级即时队列 | 全部健康候选中满足硬容量的端点 |
| 普通请求，模型候选池非繁忙 | 进入普通即时队列 | 当前不繁忙且满足硬容量的端点 |
| 普通请求，模型候选池繁忙 | 进入短窗口，聚合并排序后提交 | 全部健康候选中满足硬容量的端点 |

即时调度表示不等待窗口聚合，不保证请求立即开始执行。没有可预留资源时，高优先级请求也必须等待。调度路径及端点范围在接入时确定，实际派发时再根据最新状态过滤候选。

## 4. 繁忙窗口聚合、请求分类与排序

### 4.1 窗口释放

繁忙时，普通请求进入同一个短时间窗口。窗口从第一条请求的到达时刻开始计时，后来到达的成员不重置截止时间；达到最大成员数或最大等待时间时释放。当前调度配置为最多 16 条请求、最大聚合等待 20 毫秒。

本地模拟在输入结束时还会释放不足一批的剩余窗口。在线调用方需要根据调度器提供的下一唤醒时刻调用 `tick`，推进窗口截止及资源恢复。

窗口限制的是聚合阶段的等待时间。释放后仍可能由于硬容量、健康或冷却条件等待，因此 20 毫秒不是请求总排队时间上限。

### 4.2 重请求分类

默认排序区分轻请求和重请求。输入长度达到 `input_threshold_tokens` 时判定为输入重；当前配置阈值为 40342.5 Token。输出重分类支持固定 Token 门槛、固定百分位门槛和动态百分位门槛，当前配置使用动态百分位方式。

输出百分位来自冻结的历史长度参考，其右连续经验分布定义为：

\[
F(x)=\frac{\#\{l_i\leq x\}}{N}
\]

将预计输出长度代入 F，所得百分位达到当前门槛时判定为输出重。输入重或输出重任一成立，则判定为重请求。当前参考包含 5186 个历史样本；它在运行期间保持固定，动态变化的是分类门槛。百分位表示历史长度排名，不是输出长度预测，也不是尾部超限概率。

动态分类在即时接入或窗口释放时，读取调度器的全部端点快照、已就绪请求数和当前分类批次。设总并发容量为 C、已占用槽位为 O、已就绪请求数为 Q、当前批次大小为 B，则：

\[
U=O/C,\qquad D=\max(0,Q+B-(C-O))
\]

U 为聚合并发利用率，D 为当前已经到达的需求超过空闲槽位的数量，不包含未来尚未到达的请求。当前规则按以下优先顺序确定压力与百分位门槛：

| 压力级别 | 条件 | 输出重门槛 |
| --- | --- | --- |
| critical | `D ≥ C×1.0` | 0.6 |
| busy | 未达到 critical，且 `D>0` 或 `U≥0.85` | 0.7 |
| normal | 未达到上述条件，且 `U≥0.60` | 0.8 |
| idle | 其余情况 | 0.9 |

任何端点的并发上限未知时，当前实现使用 normal 对应门槛，并将无法可靠计算的容量指标置为未知。分类结果在当前请求或批次确定后冻结，不因随后状态变化反复改变。

上述 pressure_rules 使用并发槽位，是为了描述当前已到达请求的执行压力；RPM/TPM 软阈值继续由繁忙判断模块独立处理。两者既有不同输入，也有不同作用。

### 4.3 排序策略与顺序派发

默认 `light_heavy` 的排序键是 `(-priority, heavy)`，并保持同键请求的到达顺序。高优先级请求绕过窗口，因此当前实际窗口只含低优先级请求，排序效果是轻请求在前、重请求在后，同类保持到达顺序。它不会在轻请求或重请求内部继续按 Token 长度升序。模拟和核心直接使用同一排序器、同一标准请求，排序读到的输出长度始终是预测值。

该策略实现为 policies/light_heavy_ranking.py 中的 LightHeavyRankingPolicy，内部统一组织压力分档、门槛选择、轻重分类及排序。调度器通过 rank_requests 提供端点快照、当前时刻、已就绪请求数与批次信息，策略返回 RankingResult：有序请求、逐请求分类及压力快照。调度器仅校验、记录与派发，不提前运行独立分类器。即时请求通过可选 classify_requests 接口保留分类记录，不进入排序窗口。切换 FIFO 或加权长度策略时不执行轻重分类，未分类标签记录为 null。

项目还提供 `fifo` 和 `weighted_length`。加权长度策略直接计算：

\[
S(x)=w_{in}n_{in}(x)+w_{out}\hat n_{out}(x)
\]

权重与升序、降序可以配置；当前没有将长度归一化并转换为 0～100 分的实现。默认策略也不是加权长度排序，而是优先级加轻重分类。

排序策略必须返回每条窗口请求且仅返回一次。顺序确定后，派发器逐条重新检查候选、选择端点并预留资源，后续请求基于已经更新的状态进行判断。窗口队首暂不可派发时，后续窗口请求等待，不越过队首；即时队列则可跳过暂不可派发的成员，继续检查其他请求。

窗口不合并多个 Prompt，也不执行推理服务端的 GPU Batching。它控制路由与资源预留的先后顺序，已经派发的请求可以并发执行。

## 5. 统一 Endpoint 选择与策略扩展接口

三条调度路径最终进入同一个 Router。Router 接收单条标准请求和最新可行候选，同时向策略提供当前时间、候选端点的静态配置及近期历史统计。

当前默认 `min_rpm` 选择滚动窗口请求数与 RPM 上限之比最小的端点：

\[
e^*=\arg\min_{e\in E_{feasible}} R_e/R_e^{max}
\]

比较结果相同时，按照候选集合的既有顺序选择。若某端点 RPM 上限未知，该端点使用窗口请求数作为比较值。当前默认离线配置的 RPM 上限均已知。

每次选择仅返回一个端点标识，Router 会验证该标识确实属于当前可行候选，再生成 RouteDecision。decision 中的 `candidate_ids` 是本次可行候选记录，不是按评分排序的备用列表，也不意味着会尝试其他端点。

价格、历史 E2E/TTFT/TPOT 和请求 SLO 已可由可替换策略读取，但默认 min_rpm 尚未使用这些信息估算请求成本、预测性能或筛选 SLO。当前没有维护 Pareto Frontier，也没有成本–性能线性评分、最多三个有序备用端点或历史证据不足的回退选择机制。

后续策略可以通过 `select_endpoint(request, endpoints, context)` 接入，在同一候选和状态框架中实现请求级成本估计、条件化性能估计及 SLO 感知选择。此类算法需要另行实现并验证，不属于当前基线行为。

## 6. 资源预留、执行反馈与等待恢复

端点选定后，统一状态管理器在派发前预留一次请求额度、输入与预计输出 Token 总量，以及一个并发槽。对于已知容量，预留条件为：

\[
R_e<R_e^{max},\qquad
T_e+n_{in}(x)+\hat n_{out}(x)\leq T_e^{max},\qquad
N_e<C_e
\]

预留完成后，后续路由立即看到资源变化。核心以串行状态操作运行，本身不提供跨线程或跨进程事务；多线程接入层需要统一同步候选检查、状态更新和预留。不能仅共享状态对象就假定容量操作具有并发安全性。

核心输出 RouteDecision，执行器据此安排执行并返回 ExecutionResult。反馈包含请求标识、执行端点、成功状态、开始与完成时间，以及可选的实际 Token 使用量和时延指标。

反馈到达后释放并发，并以实际输入和输出长度修正此前的预留。没有观测到的实际长度继续沿用原估计。若对应额度记录已经过期，迟到反馈不将其重新加入当前窗口；累计用量仍按实际或保留估计修正。实际输出大于估计时，TPM 可能在反馈后超限，后续请求等待额度恢复，已执行输出不会因预留不足被回溯截断。

重复反馈、未知请求，以及端点或开始时间不匹配的反馈会被拒绝。迟到反馈不会使状态时钟倒退。有效反馈更新执行记录和历史缓存，并推动等待队列继续派发。

恢复派发时，派发器先检查高优先级即时队列，再检查普通即时队列，最后处理窗口队列。每次尝试均以最新状态重新过滤。额度和冷却恢复可通过下一唤醒时刻驱动；健康标记恢复则需要外部状态更新后再推进调度。

执行失败会更新失败统计。`endpoint` 和 `rate_limit` 类型失败进入可配置 Cooldown，当前默认时长为 1000 毫秒；请求参数错误或取消不自动触发此类冷却。行政健康标记由外部维护，普通执行失败不会自动将其永久改为不健康。

等待资源后再次尝试派发，与已经执行失败后重新发送属于不同机制。当前核心支持前者；已经返回失败反馈的请求被标记为 failed，不会自动重新排队。最大重试次数、剩余 SLO/成本预算、流式部分输出后的重启或拼接恢复均尚未实现。

## 7. 本地模拟、结果记录与当前实现范围

本地模拟将数据处理、流量生成和服务时间模型放在核心之外，使用虚拟毫秒时钟驱动到达、窗口截止、资源恢复和完成事件。同一时刻先处理已经完成的请求，再提交到达请求，随后推进窗口及等待队列。

模拟执行器根据配置的固定时延、输入处理速率、输出生成速率以及可选抖动计算服务时长，使用数据集中记录的实际长度产生反馈。默认执行器产生成功完成事件；失败与冷却处理需要注入相应执行器、状态变化或反馈进行实验，不能将默认回放视为已经验证了故障恢复。

RunResult 在内存中保留请求、事件、批次、端点快照、汇总统计和历史指标。请求结果区分窗口等待、容量等待、总排队时间和服务时间，端到端时延由到达到完成计算。文件输出包括按实际派发顺序保存的本地路由交付记录，以及逐请求的标准参数和模拟结果日志。

项目当前没有网页可视化和自动报表导出。算法效果需要通过不同到达模式、长度分布、估计误差及容量条件进行对比，不能仅凭一次回放推断已经降低成本或提升 SLO 达成率。

虚拟排程由主线调用 simulation/replay.py 的 execute，端点能力由调用方注入；独立离线命令与静态模拟端点文件已移除。当前请求配置默认采用 burst 到达模式：将部分请求集中到较短的虚拟时间段内，用于观察压力变化；它不等同于对外部服务真实压测，也不表示调度器强制将所有请求置于繁忙窗口。

当前实现已经形成“请求特征与动态状态 → 候选过滤和路径选择 → 窗口排序及统一路由 → 资源预留 → 执行反馈”的调度闭环。SLO、价格和性能上下文为进一步研究提供接口；成本–性能 Pareto 优化与有界失败重试仍需作为独立策略和恢复模块补充。
